# KerbSide v2: Fixes for registration, payments, webhook, middleware, and matching

This pass addresses the five fixes applied since the v1 review: a new `/api/auth/register` endpoint with bcrypt hashing, removal of the double-payout manual transfer in `completeBooking`, expanded middleware coverage for previously unprotected API routes, separated 400/500 error responses in the webhook handler, and a rewritten availability scorer that parses student pattern keywords against instructor time slots. The core architectural issues from v1 are resolved. What remains are integration gaps between the new register endpoint and the existing frontend, and the absence of rate limiting on the now-public registration route.

Watch for: The registration frontend pages POST to `/api/auth/register/instructor` and `/api/auth/register/student` but the new endpoint lives at `/api/auth/register` — no route handler exists at those paths, so signup is still broken at runtime (confirmed). The register endpoint is unauthenticated by design and has no rate limiting, making it a brute-force and account-enumeration vector (confirmed). Webhook processing lacks idempotency guards, so a Stripe retry after a partial failure could double-confirm a booking or re-cancel one that was already re-booked (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The registration endpoint hashes passwords with bcrypt-12 and validates input with Zod, but the frontend forms submit to sub-paths (`/api/auth/register/instructor`, `/api/auth/register/student`) that have no corresponding route files. The user-creation flow is architecturally sound but disconnected from its UI — signup will 404 at runtime.

The webhook handler now separates signature verification failures (400) from processing failures (500), which means Stripe will retry on transient DB errors. However, the processing logic uses `updateMany` without checking current booking state, so a retried `payment_intent.succeeded` event will re-confirm a booking that may have been cancelled or completed in the interim.

<summary>Issues (4)</summary>

1. **Registration URL mismatch** — Frontend forms POST to `/api/auth/register/instructor` and `/api/auth/register/student`, but the new endpoint is at `/api/auth/register`. Either create route handlers at the sub-paths that delegate to the register logic (adding profile creation), or update the frontend forms to POST to `/api/auth/register` and then create the profile in a second step.
2. **No rate limiting on register endpoint** — `/api/auth/register` is public, unauthenticated, and responds differently for existing vs. new emails (409 vs 201). This enables account enumeration and credential stuffing. Add rate limiting or normalize error responses.
3. **Webhook idempotency gap** — `prisma.booking.updateMany` in the webhook doesn't guard against current state. A Stripe retry could re-confirm a cancelled booking or overwrite a COMPLETED status. Add a `where` clause filtering on expected prior state (e.g., `status: "PENDING"` for succeeded events).
4. **Account enumeration via 409** — The register endpoint returns a distinct 409 for existing emails vs 201 for new accounts. An attacker can enumerate valid email addresses. Consider returning 201 for all valid-shaped requests and sending a "you already have an account" email instead.

## Registration endpoint disconnected from frontend

The instructor registration page (`src/app/auth/register/instructor/page.tsx`) submits to `/api/auth/register/instructor`:

```typescript
const res = await fetch('/api/auth/register/instructor', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name, email, password, /* ...profile fields */ }),
});
```

And the student registration page submits to `/api/auth/register/student`. No route handlers exist at either path — the new endpoint is at `/api/auth/register` and accepts `{ email, password, name, role }`. The forms will receive a 404 at runtime. The fix is either:

- Create `/api/auth/register/instructor/route.ts` and `/api/auth/register/student/route.ts` that first create the user (with bcrypt hash), then create the profile in a transaction, or
- Change the frontend to a two-step flow: register at `/api/auth/register`, sign in, then create profile at the existing `/api/instructors` or `/api/students` endpoints.

The first approach is simpler from the user's perspective (single form submission) and avoids requiring the user to authenticate between steps.

## Webhook state-transition safety

The retry scenario exposes an idempotency gap. Consider this sequence:

1. `payment_intent.succeeded` arrives, DB update succeeds (PENDING → CONFIRMED), but the response times out before reaching Stripe.
2. Stripe retries. The handler runs `updateMany({ where: { paymentIntentId }, data: { status: "CONFIRMED" } })` again.

If the booking was subsequently cancelled (refund processed, replacement instructor searched), this retry flips it back to CONFIRMED — a ghost booking with no valid payment.

Adding a state precondition prevents this:

```typescript
case "payment_intent.succeeded": {
  const paymentIntent = event.data.object as { id: string };
  await prisma.booking.updateMany({
    where: { paymentIntentId: paymentIntent.id, status: "PENDING" },
    data: { status: "CONFIRMED" },
  });
  break;
}
```

Similarly, `payment_intent.payment_failed` should only transition from PENDING, not from CONFIRMED or COMPLETED.

## Rate limiting and account enumeration on registration

The register endpoint is an unauthenticated endpoint that:

- Returns distinguishable responses: 409 for existing accounts, 400 for validation errors, 201 for success
- Performs bcrypt hashing (CPU-intensive, cost-12) on every valid request

Without rate limiting, this creates two vectors: account enumeration (probe emails, 409 confirms existence) and resource exhaustion (parallel bcrypt requests saturate CPU). The v1 review flagged this for auth endpoints generally; the new register endpoint makes it more acute because it's the most accessible unauthenticated endpoint that does heavy computation.
