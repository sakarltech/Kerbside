# KerbSide: Two-sided driving instructor marketplace (full greenfield build)

A complete Next.js 14 App Router marketplace connecting UK driving instructors with learner drivers. The implementation spans 100 files (~11k lines): Prisma schema with 9 models, NextAuth credentials auth with JWT sessions, a weighted scoring matching engine, Stripe Connect payment flow with 15% platform commission, privacy-gated messaging, progress tracking, and instructor continuity on cancellation. Frontend covers landing, auth flows, role-based dashboards, booking, and messaging. Infrastructure includes Docker multi-stage build, GitHub Actions CI, and a Jest test suite.

Watch for: Passwords are stored via bcrypt but the registration API routes never hash them before writing to the database (confirmed). The middleware protects `/api/bookings` and `/api/messages` but leaves `/api/instructors`, `/api/students`, `/api/progress`, `/api/admin`, and `/api/payments` unprotected at the middleware layer — route-level `getServerSession` checks exist but the asymmetry creates a defense-in-depth gap (confirmed). The matching engine's availability scoring is a slot-count heuristic that ignores actual time overlap with the student's pattern (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Authentication uses credentials-only NextAuth with JWT strategy. The auth library correctly validates passwords with bcrypt on login, but neither the instructor nor student POST registration endpoints hash the password before persisting the user record — `passwordHash` in the schema would receive a plaintext string. This is the single most critical defect in the codebase.

The matching engine weights eight factors to produce a 0–100 composite score. Location scoring uses postcode prefix matching (not geodesic distance), which works for UK postcode areas but produces a coarse binary (0 / 50 / 100). Availability scoring counts slots rather than comparing time ranges, so a student who only wants evenings gets no signal about whether an instructor's five morning slots actually overlap.

Payments flow through Stripe Connect with destination charges and a 15% application fee. The booking service creates a PaymentIntent on booking creation (PENDING state), the webhook advances to CONFIRMED on payment success, and `completeBooking` triggers a separate transfer. The double-charge risk here is that `createPaymentIntent` uses destination charges (which auto-transfer) *and* `completeBooking` creates an explicit `stripe.transfers.create` — this would pay the instructor twice for a single lesson.

Messaging enforces a booking-existence privacy gate: users can only message someone they share a booking with. The gate queries profile IDs with `|| ""` fallbacks, which means a user without a profile triggers a query with empty string IDs that will always return no match — correct fail-closed behavior, though the empty-string pattern could match a fabricated CUID in theory.

The middleware layer protects dashboard pages and two API prefixes (`/api/bookings`, `/api/messages`) but routes like `/api/progress`, `/api/admin/instructors`, and `/api/payments/connect` rely solely on in-handler session checks. This is defense-in-depth inconsistency, not a direct vulnerability, since every route handler independently validates the session.

The test suite covers the matching engine's scoring logic, Zod validators, a component render test, and API integration stubs. No tests exercise the payment flow, the booking lifecycle end-to-end, or the privacy gate in messaging.

<details>
<summary>Issues (7)</summary>

1. **Plaintext password storage** — Neither `POST /api/instructors` nor `POST /api/students` (nor any registration flow) hashes the password before writing `passwordHash` to the database. Add `bcrypt.hash(password, 12)` before `prisma.user.create`. This is a blocking issue.
2. **Double instructor payout** — `createPaymentIntent` uses Stripe destination charges (auto-transfers to connected account), then `completeBooking` creates a separate `stripe.transfers.create`. One of these must be removed or the architecture changed to manual transfers only.
3. **Middleware coverage gap** — Add `/api/progress`, `/api/admin`, `/api/payments` to the middleware matcher so unauthenticated requests are rejected before reaching handler code.
4. **Availability scoring ignores time overlap** — `calculateAvailabilityScore` only counts slots. Parse the student's `availabilityPattern` and compare against instructor time ranges to produce a meaningful signal.
5. **No rate limiting on auth endpoints** — The credentials provider and registration routes have no brute-force protection. Consider middleware-level rate limiting.
6. **Webhook signature verification runs in try/catch that returns 400** — Stripe retries on non-2xx, but transient errors (DB timeout during booking update) will also return 400 and prevent retry. Separate signature verification failures (400) from processing failures (500).
7. **Missing registration user-creation flow** — The instructor and student POST endpoints create *profiles* for existing users but no endpoint creates the `User` record with a hashed password. The registration forms submit to these endpoints but there's no user creation step.

## Password handling gap in registration

The `POST /api/instructors` and `POST /api/students` routes validate input and create profile records, but they assume a `User` record already exists (they check `session.user.id`). The registration page components (`src/app/auth/register/instructor/page.tsx`, `src/app/auth/register/student/page.tsx`) collect email and password in their forms, but the API endpoints they call don't create users — they create profiles for already-authenticated users. There is no API endpoint that accepts an email + password, hashes the password, creates a `User` record, and returns a session.

The auth flow as written has a chicken-and-egg problem: you must be authenticated to create a profile, but there's no way to create an account. The `authorize` callback in NextAuth looks up existing users by email, so new users will always fail authentication. This means the entire signup flow is broken — not just a missing hash, but a missing user-creation endpoint entirely.

```typescript
// src/app/api/instructors/route.ts POST handler
const session = await getServerSession(authOptions);
// ... requires session to exist
// ... creates InstructorProfile for session.user.id
// Never creates a User record
```

## Stripe double-payout architecture conflict

The `createPaymentIntent` function in `src/lib/stripe.ts` creates a PaymentIntent with `transfer_data.destination`, which is Stripe's destination charge pattern. When the payment succeeds, Stripe automatically transfers the net amount (minus application fee) to the connected account. No further action is needed.

However, `BookingService.completeBooking` then calls `paymentService.createTransfer` which does `stripe.transfers.create` — a second, explicit transfer to the same connected account:

```typescript
// booking-service.ts completeBooking
const instructorPayout = Math.round(
  (Number(booking.amount) - Number(booking.commission)) * 100
);
if (booking.instructor.stripeAccountId && instructorPayout > 0) {
  const transferId = await paymentService.createTransfer(
    instructorPayout,
    booking.instructor.stripeAccountId,
    bookingId
  );
}
```

The instructor receives the automatic destination-charge transfer *plus* this manual transfer. Either switch to separate charges and transfers (remove `transfer_data` from the PaymentIntent, rely on the manual transfer), or remove the manual transfer in `completeBooking` and let the destination charge handle it.

## Matching engine: location and availability approximations

Location scoring maps UK postcodes to a three-tier scale: exact match in the instructor's coverage list (100), shared 3-character prefix (50), or no match (0). This means "SW1A" vs "SW1B" scores 50 even though they're adjacent, while "SW1A" vs "SW1A" scores 100 regardless of actual distance within that postcode. For an MVP this is workable, but the 25% weight on location means the top factor in the ranking is quite coarse.

Availability scoring is a pure slot-count heuristic:

```typescript
if (instructorAvailability.length >= 5) return 80;
if (instructorAvailability.length >= 3) return 60;
return 40;
```

The student's `availabilityPattern` field (a free-text string like "evenings" or "weekends") is accepted as a parameter but never parsed or compared against the instructor's actual day/time slots. An instructor with 5 Monday 9am slots scores 80 for a student who can only do Saturday afternoons.

## Middleware and route protection asymmetry

The Next.js middleware matcher covers:
- `/dashboard/:path*`
- `/api/bookings/:path*`
- `/api/messages/:path*`
- `/api/profile/:path*`
- `/auth/:path*`

Routes not covered by middleware (no early 401 rejection):
- `/api/instructors` — GET is public (intentional for browsing), but POST requires auth (handled in-route)
- `/api/students` — both GET and POST require auth (handled in-route only)
- `/api/progress/:path*` — requires auth (handled in-route only)
- `/api/admin/instructors` — requires ADMIN role (handled in-route only)
- `/api/payments/connect` — requires auth (handled in-route only)
- `/api/payments/webhook` — must be publicly accessible (correct to exclude from middleware)
- `/api/matching` — requires auth (handled in-route only)

Every unprotected route does check `getServerSession` internally, so this isn't a direct auth bypass. The concern is defense-in-depth: a future route added under these paths could accidentally omit the session check and be exposed. The webhook endpoint correctly needs to remain outside middleware protection.

## Webhook error handling conflation

The webhook route catches all errors — including Stripe signature verification failure and downstream database errors — and returns 400 for everything:

```typescript
} catch (error) {
  return NextResponse.json(
    { success: false, error: message },
    { status: 400 }
  );
}
```

Stripe interprets 4xx as "do not retry" and 5xx as "retry later." If `prisma.booking.updateMany` fails due to a transient database timeout, the webhook returns 400, Stripe won't retry, and the booking status never advances to CONFIRMED. The signature verification should return 400 (bad request, don't retry), but processing failures should return 500 (so Stripe retries).

## Test coverage gaps

The test suite covers:
- Matching engine unit tests (score calculation, edge cases, null handling)
- Zod validator tests (all schemas, valid/invalid inputs)
- MatchCard component rendering
- API integration stubs for bookings and matching

Not tested: Stripe payment flow, webhook processing, booking lifecycle state machine, message privacy gate, admin verification workflow, instructor continuity (replacement search on cancellation), middleware auth rejection behavior. Given that the payment flow has the double-payout bug described above, integration tests here would have caught it.
